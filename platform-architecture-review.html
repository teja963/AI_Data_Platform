AI Data Engineering Career & Learning Platform

1. Current repository assessment

What exists

  • Monolithic Streamlit learning application.
  • SQL, Python, PySpark, GenAI, architecture, projects, and interview preparation.
  • PostgreSQL through SQLAlchemy, with Neon/Streamlit Cloud assumptions.
  • Bcrypt passwords, admin TOTP, Resend email, and Groq-based AI tutoring.
  • Admin approval, user activity reporting, and deployment-staleness display.

What does not exist

  • No job discovery, career-page collectors, or job matching tables.
  • No scheduler, queue, background worker, or autonomous agent runtime.
  • No Dockerfile, Docker Compose, GitHub Actions, or automated tests.
  • No external health endpoint, structured logging, monitoring, or backup automation.
  • No formal migration system such as Alembic.
Product reality The existing “AI” is synchronous Groq tutoring. The GenAI agent material is educational content; it is not currently an operational agent platform.

2. Recommended product architecture

Sources

Public ATS APIs, approved feeds, company career pages, and official government sources.

Daily worker

Fetch, snapshot, retry, normalize, deduplicate, and record source health.

Intelligence

Strict filters, semantic ranking, change detection, and cited AI summaries.

PostgreSQL

Canonical jobs, user profile, source configuration, evidence, runs, and notification state.

User experience

Job inbox, daily digest, saved/applied/rejected tracker, and learning summaries.

Do not promise “the entire internet.” Complete coverage is impossible to guarantee. Provide measurable coverage from configured organizations and supported ATS platforms. Every source should show its last successful check, discovered jobs, and collection failures.

3. Job intelligence engine

Collect

  • Run once daily at a fixed IST time.
  • Use one adapter per ATS or website family.
  • Store raw snapshots and source timestamps.
  • Retry only failed sources.

Match

  • Apply title, location, experience, and work-mode rules first.
  • Rank remaining jobs against resume skills and preferences.
  • Explain every score and exclusion.
  • Deduplicate reposted or cross-listed roles.

Notify

  • Send one daily email or Telegram digest.
  • Notify only new, high-confidence matches.
  • Keep low scores in the dashboard without email.
  • Link directly to the original application page.
Recommended MVP boundary Discover, rank, alert, and track applications. Do not automatically submit applications. Automatic submission creates accuracy, consent, CAPTCHA, and website-policy risks.

Never place website passwords in source code, GitHub, Docker Compose, or chat. If authenticated access becomes necessary, use encrypted server-side credential storage, strict source permissions, and an isolated browser process.

5. Official-source knowledge agent

Collection pipeline

  1. Maintain an approved list of government and primary technical sources.
  2. Fetch documents and record URL, publication date, retrieval time, and content hash.
  3. Compare against the previous version.
  4. Summarize only new or materially changed content.
  5. Store the evidence used to generate each summary.

Quality controls

  • Every claim links to a primary source.
  • Separate extracted facts from AI interpretation.
  • Show freshness and confidence.
  • Never let an LLM silently invent missing information.
  • Keep this pipeline separate from job collection permissions.

7. Security gate before a public domain

Critical fixes

  • Replace ?user=username restoration with signed, server-side sessions.
  • Correct email verification; do not mark unverified accounts as verified.
  • Persist OTP server-side with expiry, attempt limits, and secure random generation.
  • Add login, signup, password-reset, and AI usage rate limits.
  • Use strong password rules and secure password-reset tokens.
  • Restrict or remove the public-facing admin SQL console.

Execution and data isolation

  • Never run untrusted Python/PySpark directly inside the web container.
  • Use short-lived sandbox containers with CPU, memory, filesystem, process, and network limits.
  • Migrate interview history, editor drafts, and progress fallbacks from shared JSON into PostgreSQL.
  • Keep database and Streamlit ports private.
  • Load secrets from protected environment files or a secret manager.

8. Container delivery and automatic updates

  1. A commit is pushed to the protected main branch.
  2. GitHub Actions runs linting, tests, import checks, and a security scan.
  3. A Docker image is built and tagged with the exact commit SHA.
  4. The image is pushed to GitHub Container Registry: ghcr.io/owner/project:commit-sha.
  5. The home server detects the approved image and pulls it.
  6. Docker Compose replaces the application only after health checks pass.
  7. The previous image remains available for immediate rollback.

GHCR is a container registry, not a Git repository. A moving latest tag can exist for convenience, but deployments should record immutable commit tags.

9. Reliability and home-server operations

Availability

  • UPS with clean shutdown integration.
  • Docker restart policies.
  • External uptime monitoring.
  • Disk, memory, temperature, and certificate alerts.

Backups

  • Nightly encrypted PostgreSQL backups.
  • Off-site copy independent of the 1 TB SSD.
  • Retention policy.
  • Regular restore tests.

Network

  • Cloudflare Tunnel handles CGNAT and changing IPs.
  • No router port forwarding.
  • No public PostgreSQL port.
  • Administrative access through Tailscale or a private route.
Availability reality A UPS reduces power outages but cannot guarantee 100% uptime. ISP failure, hardware failure, disk corruption, software defects, and tunnel outages still require monitoring and recovery procedures.

11. Final recommendation

Use a simple architecture first. Keep Streamlit as the initial UI, add one separate worker, and use PostgreSQL as the single durable store. The proposed Ryzen 9 server with 32 GB RAM and 1 TB SSD does not require Kubernetes, Redis, or a large agent framework for this workload. A GPU is only needed if larger models must run locally; the existing Groq integration runs remotely.

The platform’s defensible value will not come from scraping every website. It will come from your personalized profile, transparent source coverage, precise filtering, deduplication, evidence-backed summaries, application history, and one focused daily workflow.
